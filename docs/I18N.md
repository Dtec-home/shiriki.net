# Shiriki — Internationalization (i18n)

## Status: foundation only, not live routing

This sprint (7.3) delivers a real, usable **i18n foundation** — locale
config, populated message catalogs for `en`/`sw`/`fr`, and a `next-intl`
server request config — but it does **not** cut the app over to
locale-prefixed routing (`app/[locale]/…`). That is deliberate:

1. Sprints 4/6 own `src/app/(site)/**` and `src/components/**` and were
   being edited concurrently while this sprint ran. Moving every route
   under `app/[locale]/` would touch every file those agents own and
   guarantee a merge collision.
2. A locale-routing cutover is a structural change that deserves its own
   focused sprint with a clean tree, not a bolt-on inside a sprint whose
   primary job is analytics/production-readiness.

What exists today, and works right now:

- `src/i18n/config.ts` — `LOCALES`, `DEFAULT_LOCALE`, `LOCALE_LABELS`, RTL
  helpers (all three locales are LTR today; the helper exists so adding a
  future RTL locale doesn't require an API change).
- `src/i18n/messages/{en,sw,fr}.json` — 103 real, hand-translated keys each
  (verified 1:1 key parity across all three files) covering nav, footer,
  hero, every home-page section eyebrow/heading/lead, pricing tiers, the
  contact and demo-request forms (labels + validation messages), and common
  UI strings.
- `src/i18n/request.ts` — a working `next-intl` `getRequestConfig` that
  resolves a locale from (in order) the `NEXT_LOCALE` cookie, the
  `Accept-Language` header, then `DEFAULT_LOCALE`, and loads the matching
  message file. It does not yet run on any request, because nothing wires
  it into `next.config.js` or a layout (see below).

Nothing in `src/app/**` or `src/components/**` imports from `src/i18n/**`
yet — per this sprint's ownership boundary, that wiring is the next
engineer/agent's job, not this sprint's.

## Translation quality and the `__needs_review` convention

Every string in `sw.json` and `fr.json` is a genuine translation, not a
machine gloss — written for an East African audience (Kenyan/Tanzanian
Swahili conventions; standard French as used in Rwanda/Burundi/DRC
administrative and NGO contexts). Where a phrase is idiomatic marketing
copy (a headline, a tagline) rather than a literal utility string, and a
native speaker's polish would materially improve it, the key carries a
sibling flag:

```json
{
  "heading": "Kila njia. Picha moja iliyo wazi.",
  "heading__needs_review": true
}
```

**Flagged keys, both languages** (11 keys):

| Key | Reason |
|---|---|
| `hero.headingHighlight` | Poetic marketing phrase ("beautifully connected") |
| `sections.giving.heading` | Idiomatic ("One clear picture") |
| `sections.features.lead` | Long compound sentence, includes a less-common technical loanword (`lahajedwali` / `tableurs`) |
| `sections.digitalHome.lead` | Marketing tone ("calm, capable hub") |
| `sections.security.heading` | English wordplay ("Enterprise-grade… church-simple") is hard to preserve |
| `sections.testimonials.lead` | Long compound sentence |
| `sections.cta.sub` (fr only) | Register/tone check |
| `pricing.tiers.growth.description` | Compound sentence, product terminology |
| `pricing.tiers.enterprise.description` | Compound sentence, "dioceses/multi-branch" terminology |
| `forms.demo.description` (fr only) | Register/tone check |
| `forms.demo.successTitle` | Idiom ("You're on the list") |

None of these are guesses — they are complete, grammatical translations —
they are flagged because idiomatic/marketing copy benefits from a native
speaker's final pass in a way that "Full name" → "Jina kamili" does not.
Before shipping a locale live, route these 11 keys × 2 languages (22 total)
through a native-speaker review.

**Deliberate non-translation:** the pricing tier *names* (`Starter`,
`Growth`, `Enterprise`) are kept in English in all three catalogs. This
mirrors common SaaS practice of treating tier names as product/brand nouns
(like "iPhone" or "Slack") rather than translating them — translating
`Starter` to a coined Swahili word risked sounding invented rather than
established. Revisit this if native-speaker review disagrees.

## Exact cutover plan to live locale routing

When a future sprint is ready to make one of `sw`/`fr` (or all three)
actually selectable and served:

### 1. Route restructuring
Move every file currently under `src/app/(site)/**` into
`src/app/[locale]/(site)/**`, and `src/app/layout.tsx` → keep as the true
root layout (fonts, `<html>`, analytics), with a **new**
`src/app/[locale]/layout.tsx` that:
- awaits `params: Promise<{ locale: string }>`,
- calls `setRequestLocale(locale)` (next-intl) so static rendering works,
- wraps `children` in `<NextIntlClientProvider messages={messages}>`.

Files that must move: every `page.tsx`, `layout.tsx`, `loading.tsx`,
`error.tsx`, `not-found.tsx` under `src/app/(site)/` (currently: `/`,
`/about`, `/blog`, `/blog/[slug]`, `/contact`, `/faq`, `/pricing`,
`/privacy`, `/terms`). Routes that must **NOT** move: `src/app/studio/**`
(admin tool, single locale), `src/app/api/**`, `src/app/robots.ts`,
`src/app/sitemap.ts`, `src/app/opengraph-image.tsx`, `src/app/llms.txt/**`,
`src/app/llms-full.txt/**` — these are not user-facing marketing pages and
should stay locale-neutral (or, for llms.txt, optionally locale-suffixed
later, but that is a separate decision).

### 2. Middleware
Add `src/middleware.ts`:
```ts
import createMiddleware from 'next-intl/middleware'
import { LOCALES, DEFAULT_LOCALE } from '@/i18n/config'

export default createMiddleware({
  locales: LOCALES,
  defaultLocale: DEFAULT_LOCALE,
  localePrefix: 'as-needed', // en at "/", sw/fr at "/sw", "/fr"
})

export const config = {
  matcher: ['/((?!api|studio|_next|.*\\..*).*)'],
}
```
`localePrefix: 'as-needed'` keeps `/pricing` unprefixed for the default
locale (`en`) and preserves every existing URL — no redirects needed for
current English visitors or indexed SEO URLs.

### 3. next.config.js
Wrap the existing config (owned by another agent — **do not edit it in
this sprint**) with the next-intl plugin:
```ts
import createNextIntlPlugin from 'next-intl/plugin'
const withNextIntl = createNextIntlPlugin('./src/i18n/request.ts')
export default withNextIntl(nextConfig)
```

### 4. Update every internal `<Link>`/`href`
`next-intl` ships a locale-aware `Link`/`useRouter`/`redirect` via
`createNavigation()` (typically placed in `src/i18n/navigation.ts`, not yet
created). Every `next/link` import across `src/components/layout/header.tsx`,
`mobile-nav.tsx`, `footer.tsx`, and all `src/app/(site)/**` pages must swap
to the locale-aware equivalent, or links will silently drop the locale
prefix on navigation.

### 5. `hreflang` alternates — `buildMetadata`, `sitemap.ts`, `robots.ts`
- **`src/lib/metadata.ts`** (`buildMetadata`): add an `alternates.languages`
  map to the returned `Metadata`, e.g.
  ```ts
  alternates: {
    canonical: absoluteUrl(path),
    languages: {
      en: absoluteUrl(path),
      sw: absoluteUrl(`/sw${path === '/' ? '' : path}`),
      fr: absoluteUrl(`/fr${path === '/' ? '' : path}`),
      'x-default': absoluteUrl(path),
    },
  }
  ```
  This requires `buildMetadata` to know the current locale (pass it as a
  new optional arg) — a **breaking-ish, additive** change to its signature
  that the owning agent should make, not this sprint.
- **`src/app/sitemap.ts`**: for every entry in `STATIC_ROUTES`, emit one
  `MetadataRoute.Sitemap` entry per locale (or use the `alternates.languages`
  field Next.js's sitemap type supports) so `sw`/`fr` URLs are discoverable.
- **`src/app/robots.ts`**: no change needed — robots.txt governs crawling,
  not language variants; `hreflang` is a metadata/sitemap concern only.

### 6. Sanity content localization — recommendation
Two standard approaches exist:

- **Field-level** (`{en: '...', sw: '...', fr: '...'}` object per
  translatable field, via `@sanity/document-internationalization` or a
  hand-rolled localized-object field type). Pros: one document per page/post,
  easy to see translation completeness in the Studio, no risk of a locale
  document silently going stale. Cons: schema for every text field grows
  more complex; GROQ queries must select `field.en`/`field[$locale]`.
- **Document-level** (a separate `post` document per locale, linked via a
  shared `translationKey` / `i18n.base` reference, per Sanity's
  `@sanity/document-internationalization` plugin's default mode). Pros:
  editors can localize an entire document independently and even have
  different publish schedules per locale; works well for the blog where
  posts may not have a 1:1 translation. Cons: risk of drift between locale
  documents (fields added to `en` don't automatically prompt `sw`/`fr`
  updates), more documents to manage in Studio.

**Recommendation:** field-level localization for `siteSettings`, `homePage`,
`pricingPage`, `legalPage`, `faq`, `feature`, `givingChannel`, and
`testimonial` (short, structured, always-translate-together content) —
and **document-level** (via `translationKey` on `post`) for the blog,
since blog posts are editorial content that may reasonably exist in only
one language, or be translated on a different schedule than they're
written. This matches how most Sanity + next-intl marketing sites in
practice split "product chrome" (field-level) from "editorial content"
(document-level).

## What this sprint intentionally did NOT do

- No `middleware.ts` (would intercept every route in the app today).
- No `next.config.js` edit (owned by another sprint; wrapping it with the
  next-intl plugin is inert until `[locale]` routes exist to feed it).
- No component changes — no `useTranslations()` calls anywhere in
  `src/components/**` or `src/app/(site)/**` (out of this sprint's file
  ownership).
- No Sanity schema changes for localized fields (that's Sprint 2's
  ownership; see recommendation above for when it happens).
- No locale switcher UI component (would need to live in
  `src/components/layout/header.tsx`, out of ownership).
